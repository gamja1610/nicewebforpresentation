# skillweb — 발표자료 생성 스킬

> **설치 직후 주의**: 깃허브 링크(zip 등)로 이 스킬을 방금 받아서 `.claude/skills/skillweb` 폴더에 새로 넣었다면, **지금 열려 있는 Claude Code 세션에는 반영되지 않는다.** 스킬 목록은 세션이 시작될 때 한 번 스캔되기 때문에, 세션을 닫고 새로 열어야(=새 대화를 시작해야) `/skillweb`이 목록에 나타나고 정상 동작한다. "명령어를 쳤는데 인식을 못 한다"면 새 스킬을 추가하는 걸 실패한 게 아니라 세션 재시작이 필요한 것뿐이니 당황하지 말 것.

## 실행 시 안내 (필수, 매 호출 첫 응답에서 수행)

이 스킬이 호출되면 실제 작업(md 분석 등)에 들어가기 전에, 아래 사용법 요약을 **대화창에 그대로 출력**한다 — 이 스킬을 처음 받은 사람(팀원에게 공유받은 경우 등)도 무엇을 준비해야 하는지 바로 알 수 있게 하기 위함이다:

```
📎 skillweb — 발표자료 생성 스킬
- 입력: 팀/프로젝트 설명이 담긴 .md 파일 1개 (정해진 템플릿 없음, 있는 정보만 사용)
- 출력: output/<team-slug>.html 단일 파일 — 화살표키(←/→)·Space·클릭으로 넘기는
  디스크리트 슬라이드 발표자료 (스크롤 원페이지 아님)
- 사용법: 팀 설명 md 파일을 전달하면서 "이걸로 발표자료 만들어줘" 라고 요청하면 됨
- 참고: 비전/얼굴/제스처 관련 프로젝트면 실시간 카메라 데모도 자동으로 포함될 수 있음
- 주의: 깃허브에서 스킬을 방금 새로 받았다면 세션을 재시작해야 정상 인식됨
```

출력 후 아래 §0부터 순서대로 진행한다.

팀이 작성한 프로젝트 설명 md를 읽고, 그 프로젝트의 정체성에 맞는 **모션그래픽이 들어간 웹 기반 발표자료(HTML 한 장)**를 만든다. 목표는 "그냥 예쁜 슬라이드"가 아니라 프로젝트가 실제로 뭘 시뮬레이션/구현했는지 보고 있는 것 같은 간지나는 비주얼이다.

## 0. 입력

- 입력은 팀이 작성한 `example.md` 형태의 자유 서술 md (정해진 템플릿 없음 — 팀명, 주제, 한줄 설명, 문제의식, 핵심 기능, 사용 기술, 데모/스크린샷, 팀원 등이 섞여 있을 수 있음)
- md에 없는 정보는 지어내지 말고, 있는 정보만으로 구성한다. 정보가 부족한 섹션은 과감히 생략하거나 비주얼 위주로 채운다.
- **입력이 해커톤 프로젝트가 아니라 강의자료/기술문서(예: 회로이론 챕터, 알고리즘 설명 등)일 수도 있다.** 이 경우 "팀/문제의식/데모" 같은 섹션은 없고 대신 이론·수식·예제풀이가 촘촘하게 들어있다. 아래 §2 슬라이드 수 규칙과 §5(콘텐츠 밀도)을 반드시 함께 읽는다 — "정보 부족하니 생략"이 아니라 "정보가 조밀하니 슬라이드를 늘려서 전부 담는다" 방향으로 판단이 뒤집힌다.

## 1. 프로젝트 읽고 "핵심 은유" + "시그니처 스펙터클 모먼트" 뽑아내기

가장 중요한 단계. md를 읽고 아래를 판단한다.

1. **도메인**: AI/ML, 데이터, 컴퓨터비전, IoT/하드웨어, 핀테크, 헬스케어, 게임, 소셜 등
2. **핵심 메커니즘**: 이 프로젝트가 실제로 하는 동작을 한 문장으로 — 이게 모션그래픽의 소재가 된다.
   - 예: "실시간으로 얼굴을 인식해서 표정에 맞는 필터를 씌운다" → 카메라 입력 + 랜드마크 오버레이 애니메이션
   - 예: "여러 센서 데이터를 모아 이상탐지를 한다" → 파티클/노드가 흐르다가 이상치에서 붉게 튀는 시뮬레이션
   - 예: "LLM 에이전트들이 협업해서 문제를 푼다" → 노드 네트워크가 서로 메시지를 주고받는 그래프 애니메이션
   - 예: "조이스틱으로 무한궤도 차량을 조종하고, 향후 포탑을 단다" → 차량이 화면 안에서 실제로 전진하다가 포탑을 발사하는 시퀀스
   - 예: "휴머노이드 로봇이 사람 동작을 모방한다" → 로봇 여러 대가 등장해 동시에 포즈/군무를 맞추는 장면
3. **팔레트/톤**: 도메인에 맞는 다크 테마 + 포인트 컬러 1~2개. 감으로 정하지 말고 [references/visual-language.md](references/visual-language.md)의 "도메인 → 팔레트/모티프 매핑" 표를 먼저 확인한다 — 실제 수집한 레퍼런스 영상에서 관찰한 패턴이라 훨씬 근거가 있다 (예: 수학/알고리즘=검정+청록/분홍 단색, 프리미엄/헬스케어=무채색 그레이스케일 3D, 보안/IoT=네이비+네온 시안·마젠타, 게임/캐릭터=비비드 멀티컬러+좌하단 크레딧 바 컨벤션).
4. **시그니처 스펙터클 모먼트 (필수, 지엽적인 장식이 아니라 모든 산출물의 기본값)**: 핵심 메커니즘을 "은은한 배경 장식"으로만 두지 않는다. 최소 1곳(보통 Hero, 여유가 되면 Closing에도)에는 그 메커니즘을 **문자 그대로, 과장되게 재연하는 임팩트 순간**을 반드시 넣는다 — 화면 흔들림, 임팩트 플래시, 버스트/파편 파티클 같은 "쇼크"급 연출을 아낌없이 쓴다. 잔잔한 파티클/웨이브 배경만으로 때우는 것은 미완성으로 간주한다.
   - 도메인별 스펙터클 변주 예시(그대로 베끼지 말고 실제 md 내용에 맞게 재구성): IoT/하드웨어 → 장치가 핵심 동작(발사·이동·변형)을 실제로 수행하는 순간 / 게임·로봇 → 캐릭터·로봇이 필살기·군무를 터뜨리는 순간 / 핀테크 → 수치·그래프가 급등하며 화면이 반응하는 순간 / 헬스케어 → 심박·신호가 스파이크를 찍는 순간 / 이상탐지·보안 → 위협 감지 시 화면이 경고색으로 물드는 순간 / 멀티에이전트 → 모든 노드가 동시에 발화해 하나의 결과로 수렴하는 순간.
   - 화면 흔들림·임팩트 플래시·버스트 파티클의 검증된 재사용 코드는 [references/spectacle-fx.md](references/spectacle-fx.md)를 그대로 이식하고, 좌표·색·트리거 조건·주기만 프로젝트에 맞게 바꾼다. 매번 새로 설계하지 않는다.
5. **"그래프를 보여주기"가 아니라 "현상을 시뮬레이션하기" (실제 사용자 피드백으로 확인된 기준, 모든 산출물의 최우선 원칙)**: 모션그래픽이 그 슬라이드가 설명하는 개념을 추상적으로 요약한 시각화(꺾은선 그래프가 그려진다, 막대가 올라간다, 화살표가 회전한다, 수식이 페이드인한다)에 머무르면 "단순히 효과/그래프를 보여주기만 한다"는 평가를 받는다. 대신 그 현상이 **실제로 일어나는 장면을 보고 있는 것 같은 시뮬레이션**으로 표현한다 — 파라미터를 장식이 아니라 실제 물리량/데이터값에 논리적으로 연동시킨다.
   - 나쁜 예: 전류-전압 위상차를 숫자(θ=30°)나 정적 다이어그램으로만 표시.
   - 좋은 예: 전압/전류를 실제로 흐르는 입자·파동으로 그리고, 그 위상차 때문에 에너지가 소자와 전원 사이를 왕복(반사)하는 걸 입자가 실제로 오가는 흐름으로 보여준다.
   - 나쁜 예: 계산 결과(P=160W)를 텍스트 카드로만 나열.
   - 좋은 예: 그 전력만큼 에너지 입자가 소자를 통과하며 실제로 소비/발열되는 시뮬레이션.
   - **이 원칙은 강의자료·기술문서(§5)에만 적용되는 게 아니다 — md에 숫자·측정값·알고리즘 동작이 하나라도 있는 슬라이드는 전부 이 방식으로 우선 판단한다.** 해커톤 프로젝트도 예외 없다: 센서 값이 있으면 그 값이 실제로 흐르는 파형/입자로, 정확도·지연시간·처리량 같은 지표가 있으면 그 숫자가 결정하는 속도·밀도·진폭으로, 이상탐지 임계값이 있으면 그 임계값을 넘는 순간 실제로 튀는 입자로 — "장식용 파티클 배경 + 텍스트 카드"가 기본 선택지가 아니라 **최후의 수단**이 되도록 판단 순서를 뒤집는다. 실제 수치가 하나도 없는 슬라이드(팀 크레딧, 순수 타이틀 등)에서만 canvas-particles.md류 장식 패턴을 기본값으로 쓴다.
   - 계산 과정과 수치는 MathJax로 정확히 담되, 그 옆/배경의 모션그래픽은 수식 재생이 아니라 그 수식이 나타내는 물리적/데이터 흐름의 시뮬레이션이어야 한다.
   - **구현 코드는 즉흥으로 설계하지 않고 [references/physics-sim.md](references/physics-sim.md)를 §4 어떤 다른 레퍼런스보다 먼저 확인한다 (canvas-particles.md보다도 먼저).** 위상차 파동/왕복 에너지 입자, 감쇠진동(RLC 과도응답·스프링-댐퍼), 실제 필드 공식을 따라 흐르는 입자, 주파수 응답 스윕(보드선도) 4개 패턴이 파라미터에 실제 물리량(진폭·위상·감쇠비·전달함수)을 그대로 대입하도록 만들어져 있고, 회로/역학 외의 도메인(센서 임계값, 지표 추세, 신뢰도 점수 등)에도 "실제 공식/데이터값 → 좌표·속도·투명도로 직접 매핑"하는 구조를 그대로 재사용할 수 있다. 한 덱 안에서 이 패턴을 하나만 쓰고 끝내지 않는다 — 수치가 등장하는 슬라이드마다 매번 적용한다.

이 은유와 스펙터클 모먼트를 타이틀 슬라이드(및 필요시 클로징)의 배경 애니메이션으로 만든다. 모든 팀에 똑같은 파티클 배경이나 똑같은 스펙터클을 복붙하지 않는다 — 프로젝트마다 다른 그래픽, 다른 임팩트 순간이 나와야 검증 통과.

## 2. 구조 — 반드시 "진짜 슬라이드"로 만든다 (스크롤 원페이지 금지)

최종 결과물은 **PPT처럼 한 번에 한 장만 화면 전체(100vw × 100vh)에 보이는 디스크리트 슬라이드**여야 한다. 스크롤해서 쭉 내려가는 방식은 쓰지 않는다 — 발표자가 화살표키/클릭으로 "다음 장"을 넘기는 조작감이 나와야 검증 통과.

**필수 구현 규칙**:
- 슬라이드는 `<section class="slide">` 같은 고정 컨테이너로 각각 만들고, 한 번에 하나만 `display:flex`(또는 `visible`), 나머지는 `display:none` 처리. 절대 전체 슬라이드를 세로로 이어붙여 스크롤시키지 않는다.
- 현재 슬라이드 인덱스를 JS 변수로 관리하고, `→`/`Space`/클릭으로 다음 슬라이드, `←`로 이전 슬라이드로 이동.
- 슬라이드 전환 시 트랜지션(페이드/슬라이드/스케일 중 프로젝트 톤에 맞는 것)을 넣어 전환 자체도 모션그래픽의 일부로 취급한다.
- 우측 하단 또는 좌측에 진행 인디케이터(점, 프로그레스 바, "3/6" 등)를 표시해 몇 장 중 몇 번째인지 보이게 한다.
- 각 슬라이드에 진입할 때(`slide-enter`) 그 슬라이드 내부 요소들이 등장 애니메이션으로 나타나야 한다 (스크롤 트리거가 아니라 "슬라이드 전환 트리거"로 애니메이션 실행).
- **모션그래픽을 처음 1~3장에만 몰아넣지 않는다.** 실제 사용자 피드백으로 확인된 실패 패턴: Hero/Problem 슬라이드에만 캔버스 애니메이션을 넣고 나머지 절반 이상을 텍스트/카드로만 채우면 "심심하다"는 평가를 받는다. **모든 슬라이드에 캔버스(또는 최소한 살아있는 CSS/SVG 모션 요소)를 하나씩 배정한다** — 텍스트만 있는 슬라이드가 3장 이상 연속되면 실패로 간주.
- **캔버스를 배정할 때마다 먼저 묻는다: 이 슬라이드에 실제 수치·메커니즘이 있는가?** 있으면 [references/physics-sim.md](references/physics-sim.md) 패턴(또는 그 구조를 본뜬 커스텀 시뮬레이션)을 기본으로 쓴다. 없는 슬라이드(순수 타이틀, 팀 크레딧 등)에서만 canvas-particles.md의 장식용 패턴으로 채운다. 다만 모든 슬라이드가 똑같이 무거운 3D/시뮬레이션일 필요는 없다: 핵심 슬라이드 몇 개만 진하게 만들고, 나머지는 슬라이드마다 서로 다른 가벼운 패턴을 돌려써서 다양성과 가벼움을 동시에 잡는다.

**슬라이드 구성 (5~7장, 단 §5 콘텐츠 밀도 규칙 적용 시 12~18장까지 확장 가능)**:
1. **Hero**: 팀명 + 프로젝트 타이틀 + 한 줄 후킹 카피. 위 1단계에서 뽑은 핵심 은유 애니메이션이 풀스크린 배경으로 재생.
2. **Problem**: 왜 만들었는지. 텍스트는 최소화하고 슬라이드 진입 애니메이션으로 강조.
3. **Solution / How it works**: 핵심 기능 3~4개를 카드나 다이어그램으로. 가능하면 위 은유 애니메이션의 변주(줌인/디테일 버전)를 재사용.
4. **Live Demo** (해당되면): §3의 실시간 카메라 위젯 삽입.
5. **Tech Stack**: 팀 md에 로고 이미지/링크가 있으면 그걸 쓰고, 없으면(대부분의 경우) 실제 브랜드 로고를 찾으러 가지 말고 기술명 텍스트를 뱃지/필(pill) 형태로 스타일링해서 나열 — 팀마다 스택이 다르므로 공용 로고 세트는 만들지 않는다. 하나씩 스태거 애니메이션으로 등장.
6. **Impact / Closing**: 임팩트 or 다음 단계. 팀원 크레딧.

정보가 없는 섹션(예: 팀원 미기재)은 생략하고 슬라이드 수를 줄인다.

구현 코드는 [references/camera-mediapipe.md](references/camera-mediapipe.md)를 그대로 따른다.

1. **[references/physics-sim.md](references/physics-sim.md) (수치·메커니즘이 있는 모든 슬라이드의 1순위)**: 위상차 파동, 감쇠진동, 실제 필드 공식 기반 입자 흐름, 주파수 응답 스윕 등 파라미터가 실제 물리량/데이터값에 연동된 검증된 시뮬레이션 코드. 회로/역학뿐 아니라 센서 임계값, 지표 추세, 신뢰도 점수 등에도 같은 구조로 확장해서 쓴다. §1-5 원칙을 구현하는 기본 선택지 — canvas-particles.md보다 항상 먼저 확인한다.

4. **[references/slide-engine.md](references/slide-engine.md)**: 모든 산출물이 공통으로 쓰는 슬라이드 전환 엔진 + GSAP 등장 애니메이션. §2의 슬라이드 규칙은 이 파일 기준으로 구현한다.
5. **[references/threejs.md](references/threejs.md)**: 3D가 실제로 필요한 프로젝트(공간/3D 데이터/게임)만. 사용자가 "입체 덩어리가 돌아간다/여러 각도에서 보인다" 같은 표현으로 **3D를 명시적으로 요구**하면, 배경 장식용 추상 오브젝트 하나로 때우지 말고 **개념 자체를 3D로 표현**하는 걸 우선 고려한다(예: 코일을 실제 3D 와이어프레임 두 개로, s-평면을 극점/영점이 찍힌 3D 지형으로, 3상 벡터를 회전하는 3D 페이저로). **"핵심 슬라이드 4~6개만"이라는 예전 상한은 참고용 최소치일 뿐 절대 상한이 아니다** — threejs.md의 레지스트리(lazy init + `slide-enter`/이탈 시 정지·dispose) 패턴을 쓰면 한 번에 WebGL 컨텍스트가 정확히 하나만 살아있으므로, 씬이 10개든 슬라이드 전체든 개수 자체는 성능 병목이 아니다. 3D로 표현했을 때 그 개념이 실제로 더 잘 전달되는 슬라이드라면(공간/회전/각도가 의미를 가지는 모든 곳 — 벡터·페이저·장(field)·지형화 가능한 함수·기구 구조 등) 개수를 아끼지 말고 적극적으로 3D를 쓴다. 다만 텍스트/표 위주라 3D로 바꿔도 얻을 게 없는 슬라이드까지 억지로 3D화하지는 않는다 — 기준은 "몇 개까지만"이 아니라 "이 개념이 3D로 표현될 때 더 명확한가"이다. **3D(WebGL) 렌더러는 반드시 한 번에 하나만 활성화**하고 `slide-enter`/이탈 시 정지·dispose하는 규칙은 여전히 필수 — 여러 Three.js 씬을 동시에 살려두면 노트북에서 버벅인다. 구체적인 멀티슬라이드 씬 관리 패턴은 threejs.md에 정리되어 있다.
   - **IoT/하드웨어처럼 프로젝트 자체가 실물 장치인 덱은 3D 후보를 한 곳만 찾고 멈추지 않는다 — 다음 카테고리를 전부 훑어서 해당하는 곳마다 3D를 적용한다(합치면 보통 덱의 40~50%에 도달한다):** (1) Hero/Closing — 장치 자체를 회전시키며 보여주는 배경 씬, (2) 부품/제작 슬라이드 — 실제 구매 부품·구성요소 개수만큼의 지오메트리가 모여 회전하는 `initTumblingChunks`류 장면, (3) 구성요소·구조 설명 슬라이드 — 여러 파트(바퀴/기어/서스펜션 등)의 공간적 배치 자체가 내용인 곳, (4) 고비/챌린지 슬라이드 중 **기하학적 결함**이 소재인 항목(축 편심, 정렬 오차, 뒤틀림 등) — 결함이 "왜 문제인지"가 각도/회전으로만 설명되는 경우 3D 하나로 즉시 이해된다. 반대로 스펙 표·전원/통신 흐름처럼 **수치가 핵심이라 §1-5(physics-sim.md)가 이미 담당하는 슬라이드는 3D로 바꾸지 않는다** — 두 원칙은 같은 슬라이드를 두고 경쟁하지 않고, "수치 흐름이 내용이면 physics-sim, 공간 배치가 내용이면 threejs"로 서로 다른 슬라이드를 나눠 맡는다.
6. **[references/p5js.md](references/p5js.md)**: 수학적/생성예술 느낌의 시뮬레이션(노이즈 필드 등)이 physics-sim.md/canvas-particles.md만으로 부족할 때.
7. **[references/manim-web.md](references/manim-web.md) (JS/Pyodide 연결 코드) + [references/manim-python-scenes.md](references/manim-python-scenes.md) (실제 Manim Python Scene 코드) — Manim 특유의 수학 벡터 애니메이션이 필요한 팀은 이 조합 사용을 필수로 고정한다.** 수학/알고리즘/기하학이 프로젝트 정체성 그 자체인 팀(예: 수학 시각화, 알고리즘 설명)이라면 JS로 어설프게 흉내내지 말고 manim-web.md의 검증된 Pyodide 연결 코드에 manim-python-scenes.md의 실제 Manim 문법(Scene/Circle/MathTex 등) Scene 코드를 그대로 끼워 넣어 렌더링한다. 그 외 팀은 1~6번으로 충분.
8. **[references/camera-mediapipe.md](references/camera-mediapipe.md)**: §3 실시간 카메라 구현 시 이 파일의 코드를 사용한다.
9. **[references/typography.md](references/typography.md)**: 폰트(Pretendard CDN), 헤드라인/캡션 크기 대비 규칙, 면+외곽선 겹침 타이틀, 마퀴 테두리, 하단 캡션 바, 로고 리빌 시퀀스 등 텍스트 연출 코드. 모든 슬라이드의 텍스트는 이 파일 기준으로 스타일링한다 (특히 Hero 타이틀과 팀 크레딧).

## 5. 콘텐츠가 조밀한 인풋(강의자료·기술문서) 다루기

§0에서 언급한 것처럼 인풋이 해커톤 md가 아니라 촘촘한 이론/수식/예제풀이형 문서일 때 적용하는 규칙. **실제로 겪은 실패 사례**: 회로이론 강의 챕터(10개 섹션, 예제 5개 이상)를 4~5슬라이드로 뭉뚱그렸다가 "부실하다"는 평가를 받고 전면 재작업한 적이 있다.

- **슬라이드 수는 콘텐츠 분량에 비례한다.** md의 각 대분류 섹션과 각 수치 예제(예제 13.1, 13.2, 13.8처럼 번호가 붙은 worked example)는 원칙적으로 하나 이상의 슬라이드를 배정받는다. 섹션이 길면 슬라이드를 나누고, "핵심만 요약"하며 통으로 스킵하지 않는다. 10개 섹션 문서라면 12~18슬라이드가 나오는 게 정상이다.
- **예제는 실제 숫자로.** "예제 13.8: 이상 변압기 해석"처럼 있으면 실제 입력값(120∠0°V, n=2, Z_L=20Ω)과 실제 중간 계산값(Z_in=5Ω, I1=4.8∠0°A)까지 슬라이드에 담는다. 숫자를 빼고 공식만 남기면 부실 판정.
- **수식은 MathJax로.** [references/math-notation.md](references/math-notation.md) 참고.
- **핵심 은유는 그 챕터의 물리/수학 현상에서 뽑는다** (해커톤 프로젝트가 없으니 §1의 "도메인/핵심 메커니즘" 판단 기준을 이론 챕터에 맞게 재해석 — 예: 자기결합=코일 사이를 건너뛰는 자속 에너지, 주파수응답=주파수를 스윕하며 그려지는 보드선도, 라플라스=시간영역 미분방정식이 s-영역 대수식으로 붕괴/재구성되는 순간, 푸리에=순수 사인파들이 쌓여 복잡한 파형을 합성하는 것). 이런 현상은 [references/physics-sim.md](references/physics-sim.md)의 위상차/감쇠진동/필드흐름/주파수스윕 패턴으로 대부분 커버되니 즉흥 설계 전에 먼저 확인한다.
- 이런 인풋에서도 §1의 시그니처 스펙터클 모먼트, §2의 "모션그래픽을 전체 슬라이드에 분산" 규칙은 동일하게 필수 적용된다.

## 6. 출력 형식

- 팀당 **단일 HTML 파일** (`output/<team-slug>.html`)로 출력. CSS/JS는 `<style>`/`<script>` 인라인 또는 CDN 링크 — 프레젠테이션 당일 노트북에서 파일 더블클릭 또는 로컬 서버로 여는 걸 전제로 하므로 CDN 사용 가능(인터넷 연결 있다고 가정).
- 이 HTML을 열었을 때 스크롤바가 보이거나 스크롤로 다음 내용이 나오면 안 된다 — §2 규칙대로 슬라이드 전환 방식이어야 한다.
- Claude **Artifact로 게시**할 경우엔 CDN이 CSP에 막히므로 위 4번(라이브러리)을 빼고 순수 CSS/Canvas만으로 다시 구성한다.
- 반응형: 발표 화면(16:9 프로젝터)과 노트북 화면 둘 다 고려해 `vw`/`vh` 기반 레이아웃 사용.
- 다크 테마 기본, 폰트/텍스트 연출은 [references/typography.md](references/typography.md) 기준(Pretendard CDN, 헤드라인/캡션 크기 대비 등).

## 7. 검증 루프

1. `examples/<team>.md`를 읽는다.
2. 이 SKILL.md의 지침대로 `output/<team>.html`을 생성한다.
3. 생성된 결과가 프로젝트 내용과 **실제로 관련된** 그래픽인지 스스로 점검한다 (체크리스트: 은유가 프로젝트를 설명하는가? **핵심 동작을 실제로 재연하는 시그니처 스펙터클 모먼트가 있는가, 아니면 잔잔한 배경 장식뿐인가?** **슬라이드들이 그래프/수식/막대를 그리는 데서 그치지 않고, 그 현상 자체를 실제로 일어나는 장면처럼 시뮬레이션하는가(§1-5)?** **수치·공식·메커니즘이 나오는 슬라이드를 전부 세어서, 그중 physics-sim.md 계열(또는 그 구조를 따른 커스텀) 시뮬레이션을 쓴 슬라이드가 몇 개인지 확인한다 — 수치가 있는데도 canvas-particles.md 장식 패턴이나 정적 텍스트 카드로 때운 슬라이드가 하나라도 있으면 미완성으로 간주하고 그 슬라이드부터 다시 만든다.** 모든 팀이 똑같은 배경 파티클/똑같은 스펙터클을 쓰고 있진 않은가? 정보 없는 걸 지어내지 않았는가? 카메라 fallback이 있는가? **스크롤이 아니라 화살표키/클릭으로 슬라이드가 한 장씩 넘어가는가?** 진행 인디케이터가 있는가? **원본 md의 표/예제/수치를 카드 3개로 뭉개지 않고 실제로 다 담았는가 — 슬라이드 수가 원본 분량에 비례하는가?**).
3-1. **실제로 브라우저에서 열어서 확인한다 (코드만 읽고 끝내지 않는다).** 가장 흔하고 치명적인 실패는 "첫 슬라이드가 로드 시 활성화되지 않아 화면이 통째로 까맣게 보이는 것"이다 — `slide-engine.md`의 `current` 초기값이 `-1`이 아니라 `0`이면 `goTo(0)`이 아무 동작도 안 하는 채로 조용히 실패한다. 가능하면 Playwright 등으로 실제 렌더링을 스크린샷 찍어 슬라이드 1장이 실제로 보이는지 검증한다.
3-2. **캔버스 그래픽이 있는 슬라이드는 전부 방문해서 실제로 그려지는지 확인한다.** 히어로 말고 뒤쪽 슬라이드에 박힌 미니 그래프/예제 그래프가 첫 로드 시점의 `offsetWidth`를 한 번만 읽는 구조면, 그 슬라이드가 아직 비활성(`display:none`)이라 0×0으로 굳어서 화면을 아무리 넘겨도 영원히 안 보이는 사고가 실제로 있었다(한 발표자료에서 그래프 7개 중 6개가 이 이유로 전부 빈 화면이었음). 원인과 fix는 [references/slide-engine.md](references/slide-engine.md) 참고.
3-3. **제목/본문에 `\(...\)` 수식을 직접 썼다면 `<`/`>` 이스케이프를 확인한다** — `\(-1<x<1\)`처럼 안 하면 HTML 파서가 깨져서 그 제목이 렌더링 안 되고 날것으로 보인다. [references/math-notation.md](references/math-notation.md) §3 참고.
4. 통과 못하면 1단계(핵심 은유)부터 다시 잡는다 — 애니메이션 파라미터만 바꾸는 땜질 금지.
