# Skilltech — `skillweb` 스킬 구현 브리핑

## 한 줄 요약
팀 프로젝트 설명 md 하나를 넣으면, 화살표키로 넘기는 "디스크리트 슬라이드형" 웹 발표자료(단일 HTML)를 뽑아내는 Claude Code 스킬. 스크롤 원페이지 절대 금지, 모든 슬라이드에 모션그래픽 분산이 핵심 요구사항.

## 구조
```
skillweb/
├─ SKILL.md              ← 스킬 본체 (판단 로직 + 규칙)
└─ references/           ← 검증된 재사용 코드 모음 (SKILL.md가 이 파일들을 그대로 이식)
   ├─ slide-engine.md        슬라이드 전환 엔진 (핵심 뼈대)
   ├─ physics-sim.md         1순위 — 실제 물리량(위상차/감쇠비/필드공식) 연동 시뮬레이션. 수치·메커니즘이 있는 슬라이드는 전부 이걸 먼저 확인
   ├─ canvas-particles.md    수치가 없는 슬라이드(순수 타이틀/크레딧) 전용 장식 패턴
   ├─ spectacle-fx.md        화면흔들림/임팩트플래시/버스트 파티클
   ├─ threejs.md             3D가 실제로 필요한 프로젝트용
   ├─ p5js.md                수학적/생성예술 노이즈필드
   ├─ manim-web.md + manim-python-scenes.md   Pyodide+Manim 수학 벡터 애니메이션
   ├─ camera-mediapipe.md    실시간 웹캠 + 얼굴/손 랜드마크
   ├─ typography.md          폰트/타이틀연출/캡션바 컨벤션
   ├─ math-notation.md       MathJax 수식 렌더링
   └─ visual-language.md     도메인별 팔레트·모티프 매핑표 (24,000여 유튜브 레퍼런스 프레임 샘플링 결과)
```

**설계 원칙**: SKILL.md는 "무엇을, 왜, 언제" 판단하는 로직만 담고, 실제 동작하는 코드는 전부 `references/*.md`에 박아둔다. 실행할 때마다 웹에서 새로 코드를 찾지 않고 검증된 스니펫을 그대로 이식 → 파라미터(색/좌표/개수)만 프로젝트에 맞게 바꾸는 방식. CodePen/블로그 코드는 브라우저 호환성·라이선스가 검증 안 됐다는 이유로 참고만 하고 이식은 금지.

## SKILL.md 목차 (§ 번호)
| § | 내용 |
|---|---|
| 0 | 입력 형식 (해커톤 md / 강의자료 md 두 갈래) |
| 1 | 핵심 은유 + 시그니처 스펙터클 모먼트 추출 |
| 2 | 슬라이드 구조 (디스크리트 필수, 모션 분산 규칙) |
| 3 | 실시간 카메라 (비전/제스처 프로젝트만) |
| 4 | 모션그래픽 구현 스택 — references 9개 우선순위 |
| 5 | 콘텐츠 조밀한 인풋(강의자료) 처리 규칙 |
| 6 | 출력 형식 |
| 7 | 검증 루프 (반드시 브라우저 실행 확인) |

## 실제 사용 중 발견해서 규칙으로 못박은 실패 패턴들
1. **`goTo(0)` 버그**: `current` 초기값을 `0`으로 두면 `goTo(0)`이 "이미 현재 슬라이드"로 오인해 첫 슬라이드가 영원히 안 뜬다 → `-1`로 초기화 (slide-engine.md에 고정).
2. **캔버스 0×0 고정 버그**: `display:none`인 비활성 슬라이드 안 캔버스가 `offsetWidth`를 한 번만 읽으면 0으로 굳어서 나중에 슬라이드를 넘겨도 안 그려짐 → 전체화면 캔버스는 `window.innerWidth/innerHeight`, 슬라이드 내장형 캔버스는 `slide-enter` 이벤트에서 재측정.
3. **모션그래픽이 앞쪽 슬라이드에만 몰림**: Hero/Problem에만 애니메이션 넣고 나머지는 텍스트뿐이면 "심심하다" 평가 → 모든 슬라이드에 캔버스(또는 최소 살아있는 CSS/SVG 모션) 하나씩 의무 배정.
4. **콘텐츠 밀도 무시**: 강의자료 10개 섹션을 4~5슬라이드로 뭉개면 "부실" 평가 → 슬라이드 수는 원본 분량에 비례(§5), 예제는 실제 숫자까지 포함.
5. **"3D 요구"를 장식으로 오해**: 사용자가 3D를 요구하면 배경 장식 오브젝트가 아니라 프로젝트의 핵심 개념 자체(코일→실제 솔레노이드, s-평면→극점/영점 3D 지형)를 3D로 표현해야 함.
6. **MathJax `<`/`>` 이스케이프 누락**: 수식에 부등호를 이스케이프 없이 쓰면 HTML 파서가 태그로 오인해 제목 전체가 깨짐 → 항상 `&lt;`/`&gt;`.
7. **검증을 코드 리뷰로만 끝냄**: 실제로 Playwright 등으로 브라우저에 띄워 스크린샷 찍기 전까지는 "완료"로 보지 않는다 — 위 버그들이 전부 코드만 봐서는 안 보이고 실제 렌더링에서만 드러났다.
8. **"그래프/수식만 보여주기"에 머무름**: 꺾은선 그래프가 그려지거나 수식이 페이드인하는 정도로는 "단순히 효과만 보여준다"는 평가를 받는다 → 그 현상이 실제로 일어나는 장면을 보고 있는 것 같은 시뮬레이션으로 표현(예: 위상차 수치 대신 입자가 실제로 왕복하는 흐름, 계산 결과 텍스트 대신 그 값만큼 소자가 발열하는 시뮬레이션)하도록 §1-5에 못박음. 이 원칙을 뒷받침할 재사용 코드가 없었던 것도 실패 원인이라, `physics-sim.md`에 파라미터가 실제 물리량에 직접 연동되는 검증된 패턴(위상차 파동, 감쇠진동, 필드흐름, 주파수스윕)을 추가함 — canvas-particles.md의 장식용 파티클과 달리 값을 왜곡하지 않고 실제 공식을 그대로 좌표/속도에 대입.
9. **활용 빈도가 낮음 (강의자료형에만 국한됐던 문제)**: physics-sim.md를 처음 추가했을 때 "강의·기술문서형 인풋의 기본값"으로만 범위를 좁혀놔서, 해커톤 프로젝트에는 거의 안 쓰이고 다시 canvas-particles.md 장식으로 회귀하는 문제가 있었다 → §4 레퍼런스 우선순위를 뒤집어 **physics-sim.md를 canvas-particles.md보다 항상 먼저 확인하는 1순위로 승격**하고, §1-5에 "수치·측정값·알고리즘 동작이 하나라도 있으면(해커톤 포함) 무조건 이 방식부터 판단, 장식 패턴은 최후의 수단"이라고 명문화. §2/§7에도 "수치가 있는 슬라이드마다 physics-sim.md를 썼는지" 체크 항목을 추가해 슬라이드 단위로 강제함.
10. **"데이터 충실도(physics-sim)"와 "3D 여부(threejs)"를 같은 축으로 혼동**: 실제 UGV(무한궤도 차량) 프로젝트 검토 중, "실사 시뮬레이션을 늘려라"는 physics-sim.md 지침과 threejs.md의 "3D는 필요할 때만"이 서로 충돌하는 것처럼 보인다는 혼란이 있었음 — 실제로는 서로 다른 두 축이라 충돌하지 않는다: physics-sim은 "수치가 있는가"(2D/3D 무관), threejs는 "공간 배치·여러 각도가 그 자체로 내용인가"를 각각 독립적으로 판단하고, 같은 슬라이드를 두고 경쟁하지 않는다(전원/통신처럼 수치가 핵심이면 physics-sim, 부품 조립체처럼 공간 배치가 핵심이면 threejs). 이 구분과, "핵심 슬라이드 4~6개"라는 예전 3D 상한이 절대치가 아니라는 점, IoT/하드웨어 덱에서 3D 후보를 한 곳만 찾고 멈추지 말고 Hero/부품조립/구조설명/기하학적 결함 4개 카테고리를 전부 훑으라는 지침을 §4-5에 추가함.

## 배포
